# n8n Video Automation App Constitution

## Core Principles

### I. Scientific Accuracy

Every video produced by this system MUST source its factual claims exclusively from
peer-reviewed literature retrieved via the ArXiv API (or equivalent vetted academic
sources). No claim presented in narration, captions, or on-screen text may be fabricated,
hallucinated, or extrapolated beyond what the source material states.

**Rules**:
- Narration scripts MUST cite the ArXiv paper ID (e.g., `arXiv:2401.00001`) used as the
  source for each factual claim.
- Any uncertainty in the source material MUST be reflected in the output (e.g., "the
  authors suggest…" rather than declarative assertions).
- Automated pipelines MUST log source metadata (title, authors, DOI/arXiv ID, retrieval
  date) alongside every generated video asset.
- Content that cannot be sourced to a verifiable paper MUST be rejected by the pipeline,
  not approximated.

**Rationale**: Educational video content presented as science carries responsibility for
accuracy. Errors propagate widely and erode trust. Grounding every claim in citable
literature makes the system auditable and correctable.

### II. Educational Value

Every video MUST deliver clear, comprehensible explanations suitable for an informed
general audience (graduate-level layperson). Engagement or entertainment considerations
MUST NOT compromise instructional clarity.

**Rules**:
- Each video MUST have a single, clearly stated learning objective surfaced within the
  first 30 seconds.
- Technical jargon MUST be defined on first use, either in narration or on-screen text.
- Visual elements (diagrams, animations, text overlays) MUST reinforce—not distract
  from—the spoken explanation.
- Video duration MUST be scoped to the minimum required to convey the learning objective;
  padding for length is prohibited.
- The pipeline MUST produce a structured outline (topic → key concepts → conclusion)
  before generating any media asset.

**Rationale**: Educational value is the primary purpose of the system. A video that is
scientifically accurate but incomprehensible fails its audience. Requiring a learning
objective and outline gates forces intentional design before production.

### III. Copyright Compliance

All assets incorporated into any produced video MUST be either AI-generated by the
pipeline itself or sourced from explicitly royalty-free / CC0-licensed repositories. No
asset with an ambiguous or unverified license may be used.

**Rules**:
- Visual assets (images, diagrams, background footage, icons) MUST originate from one
  of the approved sources:
  1. AI-generated via a model with a permissive output license (e.g., DALL·E, Stable
     Diffusion with appropriate license).
  2. Royalty-free stock with explicit commercial reuse rights (e.g., Unsplash, Pexels,
     Pixabay under their respective licenses).
  3. Public domain / CC0 assets with documented provenance.
- Audio assets (music, SFX) MUST follow the same three-tier sourcing rule. TTS output
  from gTTS or OpenAI TTS is inherently pipeline-generated and compliant.
- The pipeline MUST record asset provenance (source URL, license type, retrieval date)
  in a machine-readable manifest (`assets-manifest.json`) for every generated video.
- Any asset failing provenance verification MUST be regenerated or replaced before
  the video is published. Publication of unverified assets is prohibited.
- ArXiv paper figures may only be used if the paper's license (e.g., CC BY 4.0) permits
  reproduction; the license MUST be verified before inclusion.

**Rationale**: Copyright infringement exposes the project to legal liability and
undermines creator trust. Strict provenance tracking ensures every published video is
defensible. AI-generation and royalty-free sourcing eliminate ambiguity at the asset
level.

## Tech Stack & Asset Constraints

### Approved Technology

| Layer | Technology | Notes |
|---|---|---|
| Orchestration | n8n | Workflow automation; all pipeline triggers and routing MUST be defined as n8n workflows |
| Video composition | Python + MoviePy | All programmatic video assembly MUST use MoviePy; no other video-editing runtime |
| Text-to-Speech | gTTS (default) / OpenAI TTS (premium) | Pipeline MUST support both; OpenAI TTS requires API key configuration |
| Content sourcing | ArXiv API | Primary and mandatory source for scientific content |
| AI image generation | OpenAI DALL·E or Stable Diffusion (self-hosted) | For generating compliant visual assets |

### Asset Pipeline Rules

- Images MUST be generated at minimum 1920×1080 resolution for video use.
- TTS audio MUST be generated at 44.1 kHz, stereo.
- All intermediate assets MUST be written to a versioned temp directory and cleaned up
  after successful video export.
- The pipeline MUST fail loudly (non-zero exit, n8n error node) on any asset generation
  failure; silent partial outputs are prohibited.

## Development Workflow

### Pipeline Stages

Every feature or change to the automation pipeline MUST follow this ordered stage gate:

1. **Outline generation** — n8n fetches ArXiv paper → Python extracts abstract + key
   claims → structured outline produced.
2. **Script generation** — narration script authored from outline; learning objective
   stated explicitly.
3. **Asset generation** — visuals generated (AI) or fetched (royalty-free); provenance
   logged.
4. **Audio generation** — TTS narration produced from script.
5. **Video composition** — MoviePy assembles assets + audio; captions overlaid.
6. **Validation gate** — manifest verified, source citations checked, output file
   inspected (duration, resolution, audio sync).
7. **Export** — final video written to output directory; manifest committed alongside.

### Quality Gates

- No video exits stage 6 unless `assets-manifest.json` is present and complete.
- No video exits stage 6 unless the ArXiv source ID is embedded in the video metadata.
- Pipeline MUST emit structured JSON logs at each stage transition for observability.

### Complexity Justification

Any addition of a new dependency, AI model, or external API MUST be documented with:
- The capability gap it fills.
- The copyright/license implications.
- The failure mode and fallback strategy.

## Governance

This constitution supersedes all other project conventions. Any practice not addressed
here defaults to the least-complex, most-auditable option.

**Amendment procedure**:
1. Propose amendment in a pull request with a `constitution-amendment` label.
2. State which principle is affected, the old rule, the new rule, and the rationale.
3. Version bump MUST follow semantic versioning (MAJOR/MINOR/PATCH) as defined above.
4. Amendment is ratified when merged to the main branch by the project owner.

**Compliance review**:
- Every PR modifying pipeline logic MUST include a "Constitution Check" section in its
  description verifying adherence to all three Core Principles.
- CI MUST validate that `assets-manifest.json` is produced for any test video generated
  during a pipeline run.

**Versioning policy**:
- MAJOR: removal or redefinition of a Core Principle.
- MINOR: addition of a new principle, section, or materially expanded guidance.
- PATCH: clarifications, wording fixes, non-semantic refinements.
